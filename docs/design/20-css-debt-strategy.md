## Classification

A single count of 1,414 literals is not actionable, because the entries carry
completely different risk. Split three ways:

### Bucket A — collides with a theme token (398 occurrences, 14 unique)

**This is the only bucket that is a correctness defect rather than untidiness.**
These literals exactly equal a themed token's value, so they look right under the
default *forest* preset and **silently fail to change under the other eight**.
Theme switching is a shipped feature; these values quietly opt out of it.

| Literal | Occurrences | Token it duplicates |
|---|---|---|
| `#fff` / `#ffffff` | 205 | `--paper`, `--on-teal`, `--on-rose`, `--on-blue` |
| `#eef4f0` | 38 | `--soft` |
| `#123b31` | 28 | `--deep`, `--gradient-mid` |
| `#117b6d` | 27 | `--teal`, `--teal-ink` |
| `#d9e4dd` | 25 | `--line` |
| `#17211b` | 25 | `--ink` |
| `#0c2f28` | 20 | `--gradient-top` |
| `#627169` | 15 | `--muted` |
| `#f7faf8` | 5 | `--bg` |
| `#b84957` | 4 | `--rose`, `--rose-ink` |
| `#92651c` | 3 | `--gold-ink` |
| `#c48725` | 2 | `--gold` |
| `#276a9f` | 1 | `--blue`, `--blue-ink` |

**`#fff` is deliberately excluded from remediation.** It maps to four different
tokens depending on meaning — page surface (`--paper`) versus accessible
foreground on a coloured fill (`--on-teal`, `--on-rose`, `--on-blue`). Only a
human reading the surrounding rule can tell which is intended, and choosing
wrongly produces a contrast failure rather than a visible mistake. A
find-and-replace here would be actively harmful.

That leaves **193 unambiguous occurrences** across ~28 files, none of which
exceeds 8 in a single file.

### Bucket B — neutral (26 unique)

Greys, black and white within 6 points of grey. Carry no brand hue, so they
rarely need a token and rarely break under a preset change. **Lowest priority.**

### Bucket C — one-off (253 unique)

Values with no token equivalent: state tints, shadows, gradient stops,
`rgba()` overlays. Each represents a **design decision that was never made** —
tokenising them requires deciding what they *mean*, not just what they equal.
This is design work, not mechanical work, and it is where most of the 1,414
occurrences live.

## Correcting the metric

Two baseline numbers were wrong, and both would have caused wasted or harmful work:

- **Viewport meta: reported 2 missing, actually 0.** `resources/views/admin.php`
  was a false positive — it renders through `_admin-shell.php`, which emits the
  tag, confirmed against the rendered output of `/admin`. Scanning files in
  isolation cannot see shell-inherited markup. The tool now distinguishes *own*
  from *inherited*. The other page, `events_rsvp/index.php`, was genuinely
  missing one and has been fixed.

- **`outline:none`: reported 12 defects, actually 1.** The replacement indicator
  is usually declared in a *separate* rule (`.x{outline:none}` then
  `.x:focus{box-shadow:…}`), so a per-rule check reports correct code as broken.
  The tool now collects indicators across the whole file before judging. A
  second artifact compounded it: shell CSS is built by PHP string concatenation,
  so selectors arrived as `. '.topbar-campus-select` and never matched their own
  indicator.

  The single remaining case is `#portal-main:focus{outline:none}` — the skip-link
  target. It is a programmatic focus destination, not an interactive control, and
  suppressing a ring around a whole page region is the conventional treatment.
  **Reviewed and intentionally retained.**

The lesson generalises: a debt metric that over-reports is worse than no metric,
because it drives churn through correct code. Every number above is now one I
have verified by inspection rather than inferred from a pattern count.

## Staged strategy

The governing constraint: **CSS regressions in this codebase have repeatedly
come from cascade order and specificity, not from wrong values.** A mass
substitution changes hundreds of rules at once, and a single specificity shift
is then indistinguishable from the rest of the diff. Every stage below is
therefore small enough to verify visually and revert independently.

**Stage 1 — Bucket A, excluding `#fff`.** 193 occurrences, ~28 files, ≤8 per
file. Replace each with its token *one file at a time*, verifying that file at
the standard viewports and across all 9 presets. Payoff is real: each file
becomes theme-correct. `tools/check-contrast.php` already gates all 135 token
pairs across 9 presets, so a wrong token is caught mechanically.

**Stage 2 — breakpoints.** 58 unique px values collapse to the 4 defined
tokens. Do this per page during that page's own work, never globally: a
breakpoint shift moves layout, and the three-gate rule (scalar + pixel +
selector-set) applies.

**Stage 3 — `#fff`, by meaning.** Only after Stage 1, and only file by file with
a human deciding `--paper` versus `--on-*` per occurrence. Contrast gate must
pass on every preset after each file.

**Stage 4 — Bucket C, opportunistically.** Tokenise a one-off value only when
already editing that rule for another reason. Never as a standalone sweep.

**Not planned:** extracting the 47 inline `<style>` blocks into a single
stylesheet. It was in the original roadmap as Phase 0, and it remains the single
highest-risk change available — it alters cascade order for every page at once,
which is precisely the failure mode this codebase is most prone to. It should
only be attempted with a visual-regression baseline in place.

## Ratchet

`reports/css-debt-inventory.json` is committed, so the numbers above are a
baseline that later work is measured against rather than an opinion. The
architecture suite already demonstrates the pattern with `$sqlDebtBaseline`:
new violations fail, and cleaning a listed file without delisting it also fails.
Applying the same ratchet to Bucket A once Stage 1 begins would prevent
regression; it is **not** applied yet, because a ratchet on a number nobody is
actively driving down only creates friction.
